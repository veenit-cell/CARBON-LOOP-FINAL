# ADR-0002: Android-First Game Architecture Pivot

- **Status:** Accepted
- **Date:** 2026-08-27
- **Approval date:** 2026-08-27
- **Project:** CarbonLoop
- **Decision owner:** Hivemind project team
- **Institutional approval:** Not granted; all real-campus approvals remain **NEEDS_VERIFICATION**
- **Related documents:** [Game Overview](../CarbonLoop_Game_Overview.md) and [Game Architecture](../CarbonLoop_Game_Architecture.md)

## Context

CarbonLoop was previously planned as a Next.js PWA-first campus decarbonization platform, with campus-shuttle transport as the primary hackathon vertical slice and electricity-bill capture as the secondary flow. The new product direction is an Android-first real-world sustainability game that turns missions into evidence-backed activity records, while preserving deterministic carbon accounting, controlled rewards, and privacy-safe institutional reporting.

Native Android capabilities are required for reliable permission flows, Health Connect access, activity recognition, mission-scoped location tracking, and offline mobile synchronization. The institutional dashboard and trusted application boundary remain web and server responsibilities. This internal Hivemind approval does not approve any real campus deployment, health-data collection, location tracking, factor, issuer, reward policy, or institutional arrangement.

## Decision

CarbonLoop adopts the following architecture and product direction for the Hivemind project and hackathon:

1. CarbonLoop is an Android-first real-world sustainability game.
2. The player application will use Kotlin and Jetpack Compose.
3. Next.js and TypeScript will be retained for the institutional dashboard and application API.
4. Supabase PostgreSQL remains the authoritative system of record.
5. The architecture remains a modular monolith with two first-party clients: Android player application and web institutional dashboard.
6. The current Next.js foundation is expected to become `apps/web`; no files are moved by this ADR.
7. The future Android application will live under `apps/android`; no Android project is generated by this ADR.
8. Eco XP, Green Reward Points, and Verified CO2e Saved are separate measures:
   - **Eco XP** is game progression, not money or a carbon claim.
   - **Green Reward Points** are controlled redeemable loyalty points issued only by trusted server rules.
   - **Verified CO2e Saved** is a reproducible avoided-emissions calculation with baseline, factor, evidence, and methodology provenance.

### Internal approval scope

This Hivemind approval covers:

## Superseded decisions

This ADR supersedes [ADR-0001](ADR-0001-mvp-scope-and-pilot-boundary.md) only for its old hackathon/MVP scope: campus-shuttle transport as the sole primary vertical slice and electricity-bill capture as the required secondary flow.

ADR-0001 is not superseded for privacy, methodology, data ownership, evidence, calculation, reward-integrity, or institutional-approval cautions. It remains a historical decision record and must not be archived or deleted as part of this pivot.

## Retained decisions

The following remain in force:

- PostgreSQL is the authoritative system of record.
- Carbon calculations are deterministic, versioned, reproducible, and never performed authoritatively by an LLM.
- Verification, calculation, reward issuance, redemptions, and privileged actions occur only on trusted server paths.
- Evidence quality, verification status, calculation results, and reward eligibility remain distinct concepts.
- Supabase Auth, Storage, PostgreSQL, and RLS remain the intended platform services.
- Institutional users receive privacy-thresholded aggregates by default.
- Green Reward Points are not carbon credits, offsets, cash, or tradable environmental assets.
- Neo4j, InfluxDB, Redis, Qdrant, blockchain, federated learning, direct UPI ingestion, real financial settlement, and unsupported live-grid or causal claims remain excluded.

## New MVP scope

The hackathon demonstration will prioritize:

1. Player onboarding and purpose-specific consent.
2. A walking mission or simulated tracking adapter.
3. Shuttle QR verification.
4. Deterministic, versioned carbon calculation.
5. Separate Eco XP and Green Reward Point results.
6. Player level and streak.
7. Mock reward redemption only.
8. Privacy-safe institutional dashboard updates.

Seeded, simulated, projected, and live data must remain visibly distinguishable. Exercise or movement may earn Eco XP but must not create a carbon-saving claim unless an eligible replacement baseline, evidence, and calculation rule are present.

Always-on GPS, iOS parity, carbon credits, blockchain, direct UPI ingestion, real financial settlement, arbitrary e-commerce purchasing, and unsupported carbon or causal claims are excluded from the hackathon scope.

## Repository consequences

The intended future structure is:

```text
apps/
  android/       # Kotlin and Jetpack Compose player application
  web/           # Next.js institutional dashboard and application API
packages/        # Published TypeScript domain interfaces and server modules
workers/         # PostgreSQL-backed job handlers when implemented
supabase/        # Future migrations, policies, and synthetic seeds
tests/           # Calculation, integration, web, and cross-client tests
docs/
```

The existing Next.js foundation will later move to `apps/web`. Domain packages must not import Android or web UI code. This ADR creates no workspace configuration, moves no files, and makes no application-code changes.

## Data and API consequences

Future data modelling must support player profiles, quest templates and runs, minimal sensor summaries, activity events, evidence records, baselines, calculations, append-only Eco XP and Green Point score events, achievements, teams, campaigns, reward items, redemptions, aggregates, jobs, and audit events.

The application API will serve both clients. Player operations will later include consent, quest lifecycle, activity/context submission, shuttle check-in, score/progress viewing, team participation, and mock reward redemption. Campus operations will later include campaign and quest configuration, evidence review, methodology/factor workflow, reward catalogue administration, aggregate reporting, and export.

All writes must apply authentication, schema validation, tenant/role authorization, purpose-specific consent checks, abuse limits, idempotency, transactional writes, and audit events. Android clients cannot issue verified evidence, authoritative calculations, points, or fulfilled redemptions.

## Privacy and security consequences

- Health/activity, route verification, bills/evidence, personalization, social participation, aggregation, and research require separate consent purposes.
- The Android app must use the least invasive mission-sufficient signal: trusted issuer events first, then permitted aggregates or activity recognition, and route capture only during explicitly started missions.
- Always-on precise location collection is prohibited. Visible pause/stop controls and permission-denial fallbacks are required.
- Raw routes and sensor data require approved minimization and retention rules; derived summaries are preferred where feasible.
- Offline submissions must be encrypted locally, pending until server verification, and protected by idempotency and plausibility checks.
- Individual leaderboards are opt-in, use chosen game names, and must not expose health, carbon, evidence-review, or precise-location data.
- Small cohorts must be suppressed in institutional and team reporting.

## Risks

| Risk | Required mitigation |
| --- | --- |
| Sensor activity is farmed for rewards | Separate Eco XP from avoided emissions; require replacement context and server-side reward rules. |
| Health or route data is over-collected | Mission-scoped consent, least-invasive signal hierarchy, short retention, and visible tracking controls. |
| Native Android scope delays the team | Keep the first demo to one walking/simulated mission, shuttle QR, mock redemption, and a seeded dashboard. |
| Reward liability exceeds budget | Use campaign caps, inventory/budget checks, append-only reversals, and mock fulfilment for the hackathon. |
| New activities create unsupported claims | Do not enable carbon rewards without an approved baseline, factor, method, evidence rule, and anti-fraud controls. |
| The game conflicts with campus reporting privacy | Compute team and dashboard progress only from privacy-safe aggregate records. |
